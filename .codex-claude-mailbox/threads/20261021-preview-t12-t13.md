# Goal

兩個預覽缺口都來自基線的隱含假設，user 已選定做法：

- T12 選 C：匯入進通用表單的代碼，不應因為登記在 `table_registry` 就被當成實體資料表。
- T13 選放寬檢查器：基線自己標為 optional kit source、缺模組時明確回 501 的匯入，不應擋住獨立組裝。

分支：`feature/preview-t12-t13`。依 CLAUDE.md，一個功能一條分支；T12 與 T13 各自獨立，分成兩個 commit。

# 已查證的事實（讀原始碼與實際組裝得到）

## T13

- 以 platform-core 加 generic-forms 為 Recipe 實際組裝，檢查器只報兩處缺口：`db_capabilities.py:186`（`app.models.core.edit_reason`）與 `:305`（`app.models.import_job`）。
- 兩處形式相同：函式內 `try: from ... import ... except Exception as exc: raise HTTPException(501, ...)`，註解為 `optional kit source`。缺模組時是明確的 501，不是崩潰，也不是靜默。
- `check_tree.py` 目前對所有 `app.*` 匯入一律要求目標存在，不分有無保護。

## T12

基線以「代碼登記在 `table_registry`」判定為實體資料表（領域表），三個判斷點：

| 位置 | 用途 | 症狀 |
|---|---|---|
| `generic-forms-kit` `routes_generic_forms.py:653` | 列出資料列 | 走實體表路徑，查詢例外被吞掉，回 0 筆 |
| `platform-core-kit` `db_capabilities.py:105` | 搜尋紀錄 | 同上 |
| `platform-core-kit` `db_capabilities.py:223` | 趨勢（analytics-kit 的 `/api/analytics/trend` 使用） | 查不存在的實體表，500 |

匯入管線的建工作需要 `table_registry` 有該代碼（`routes_import_v2.py`），匯入資料落在 `generic_records`（T9 已驗證），所以「匯入進通用表單」的代碼必然同時是站別與登記表，撞上上述判斷。

# 設計（兩項都沿用 D107 的組裝補丁機制：錨點不符即拒絕，只改組裝複本，不改 `kits/`）

## T13：檢查器

`check_tree.py` 對缺少的 `app.*` 匯入，若同時符合以下全部條件，視為「可選匯入」不報錯：

1. 匯入節點位於 `try` 區塊的主體內；
2. 每個 `except` 都捕捉 `Exception`、`ImportError` 或 `ModuleNotFoundError`（含其元組）；
3. 每個 `except` 區塊的最後一個敘述是 `raise`（缺模組時必須明確失敗）。

任一條件不符（無 `try`、`except` 只 `pass`、`except` 後繼續執行）維持報錯。被放行的缺口不靜默：輸出逐項列表，並寫進組裝報告。

## T12：補丁

在組裝複本中，把三個判斷點由「已登記」改為「已登記且實體資料表存在」，以 PostgreSQL 的 `to_regclass` 判定（預覽僅用 PostgreSQL）。真正的領域表（有實體表）行為不變；只登記、沒有實體表者落回通用路徑。

# 風險與限制（需 user 知悉）

- T12 補丁只在預覽組裝複本；`kits/` 與 Composer 產出的設定交付包不變。P2 的可執行組裝要有同樣處理，已列為 P2 輸入。
- `to_regclass` 只適用 PostgreSQL；Recipe 若為 sqlite，預覽本身不支援，不在本功能範圍。
- T13 放寬後，閘門之外多一層保護：未納入的 Kit 在閘門回 403，閘門被繞過時才會到 501。實測兩層都要驗。
- 放寬檢查器是改變 fail-closed 的語意，所以限定為「必須 raise 的 try 區塊」，並逐項列出，不做全面放行。

## 與計畫的差異（規則 7、12）

- **T13 的範圍擴大，且結論比計畫更好：** 計畫只放寬匯入檢查，預期最小集合因此縮小。實測發現還有字串外鍵（`ForeignKey("table.column")`）的硬相依，檢查器看不到，組裝通過、容器啟動才崩潰。因此新增「外鍵閉包」檢查（D122），最小可獨立集合由 5 個降為 3 個（platform-core、generic-forms、audit-edit），而不是計畫預期的「核心加通用表單」。只選核心、核心加通用表單現在於組裝階段明確拒絕。
- 舊測試 `test_recipe_assembly_runs_real_validator_and_reports_import_gap` 以「只選核心的組裝必須失敗」作為 T13 的證據，行為依決議改變後已更新為驗證最小集合成功並列出可選匯入，同時固定「只選核心」「核心加通用表單」仍拒絕。
