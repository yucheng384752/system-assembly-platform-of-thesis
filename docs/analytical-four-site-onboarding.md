# analytical-four-kit：進入全新場域，client 要填寫與上傳什麼

日期：2026-11-01
依據：Kit 原始碼與契約、`docs/analytical-four-kit.md`、Analytical-Four 的 `PROJECT_INTEGRATION_INPUT_REQUIREMENTS.md`，以及 2026-11-01 在示範資料上做的 17 組資料品質實驗（結果在第 5 節）。
性質：分析與建議。尚未用任何真實新場域的資料驗證。

## 1. 結論

1. **client 要準備三類東西：資料檔（上傳）、一份分析設定檔（填寫）、幾項 Kit 設定（填寫）。** 最低只要五樣就能開始 A 層：待分析資料、正常基準、欄位字典、品質與不良說明、製程流程說明。B、C 層再加不良代碼定義、已標註的歷史樣本、拓樸、SOP，客訴模式的 C 再加歷史案例檔與 LLM 服務位址。
2. **引擎有一批寫死的欄位名稱，client 只靠填資料無法改。** 新場域的資料欄位若不叫這些名字，目前會有三種結果：直接報錯（可接受）、悄悄略過、悄悄退化。最危險的是後兩種（第 4 節）。要讓 client 不必改自己的欄位名，Kit 需要一層欄位對照，目前沒有。
3. **多數 client 不需要提供的東西由系統產生**：基準統計、PCA、事件、向量庫、不良特徵分布庫（每日模式用已標註樣本訓練）、案例庫版本。
4. **場域導入的真正工作量在欄位對照與標籤品質**，不在上傳。建議先做小批資料的試跑，再放完整資料（第 6 節）。

## 2. 需要 client 上傳的檔案

資料目錄（`ANALYTICAL_FOUR_DATA_DIR`）內的相對路徑由分析設定檔指定，下表是示範資料的慣例。

| 檔案 | 內容 | 哪一層、哪個模式需要 | 誰準備 |
|---|---|---|---|
| 待分析資料 CSV（`data_source.current_data.descriptive`） | 每列一個分析樣本；ID、類別欄位、數值特徵、品質目標欄位 | A 必要。每日模式是一天的混合資料（依目標欄位分成待查與基準）；客訴模式是要查的樣本 | client 提供原始資料，整合方整理 |
| 正常基準 CSV（`baseline_data.descriptive`） | 已確認正常、特徵與待分析資料相同 | A：客訴模式必要；每日模式不需要（由資料分組取得） | client 判定「正常」的範圍，整合方檢查 |
| 不良代碼定義 JSON（`baseline_data.ng_code`） | 陣列，每筆 `category` 與 `details`（機台、製程、現象、原因、處置） | B 必要 | client 的品保／製程工程 |
| 已標註的歷史不良樣本 | 不單獨上傳：放進每日模式的待分析 CSV 的不良代碼欄位，由每日模式訓練出分布庫 | B 必要（沒有就沒有分布庫） | client 提供標籤，必須可信 |
| 不良特徵分布庫 `known_base.json`（`baseline_data.prescriptive`） | 由每日模式產生，也可由整合方帶入 | B 客訴模式必要 | 系統產生 |
| 製程拓樸 JSON（`baseline_data.topology`） | 站點順序、特徵 id／名稱／角色／層級 | C 必要 | client 的製程工程提供流程，整合方轉格式 |
| SOP 知識 CSV（`baseline_data.rag_knowledge`） | 七欄：編號、站點、適用特徵、問題類別、原因、處置、來源 | C 必要 | client 提供 SOP 原文，整合方擷取 |
| 歷史案例／誤判 JSONL（`case_data`） | 每行一筆案例；沒有歷史可給空檔 | C 客訴模式必要（可空） | 空檔起步，之後由回饋與案例庫版本累積；舊系統若有可經匯入 |

## 3. 需要 client 填寫的設定

### 3.1 Kit 設定（`settings.json`，管理員）

| 欄位 | 填什麼 | 注意 |
|---|---|---|
| `layers.a/b/c` | 要啟用哪些層 | B、C 需要 A；客訴模式的 C 需要 B |
| `mode` | `daily` 或 `complain` | 決定資料怎麼分組、B 層做訓練還是推估、C 層做到哪一步 |
| `analysisConfig` | 分析設定檔的路徑 | 每個場域一份 |
| `llm.endpoint` | AI 語言模型服務位址 | 事件資料會送過去；留空表示未設定；位址不可含帳密 |
| `llm.timeoutSeconds` | 逾時 | 實測 6 筆約 100 秒（本機 14B 模型），事件多要調高 |
| `llm.apiKeyEnv` | 存放金鑰的環境變數名稱 | 金鑰本身由部署端設定，不填進任何檔案 |

### 3.2 分析設定檔（原 Analytical-Four 格式）要填的內容

- `feature`：**哪些欄位是數值特徵、哪些是類別、哪個是目標、哪個是 ID。** 這是整份導入的核心。類別欄位按 Man／Machine／Material／Method／Environment／Measurement 分組。
- `method`（`IQR Thresholds`、`3sigma`、`min_max`）、`serializer`（目前只有 `UT`）、`observer`。
- `data_source` 內各檔案路徑、向量模型（`rag_setting.builder_type`：離線用 `builtin-hash`，正式用 E5）、向量庫資料夾。

client 實際要提供的是**欄位字典**，由整合方轉成上面這份設定。字典每欄要有：原始欄名、意義、型別、單位、缺值意義、角色（ID／數值／類別／目標）。

### 3.3 需要 client 決定、無法由資料推出的事

1. 一列代表什麼（產品、批次、時間窗）。
2. 「正常」的定義與基準範圍（產品規格、機台、材料、期間）。
3. 目標欄位的值各代表什麼（每日模式：值較小的那一組被當成待查，另一組當基準，顛倒會整個反過來）。
4. 不良代碼的清單與真實標籤的可信度。
5. 回饋由誰確認、誰核可（預設：管理員、經理、操作員可提交；管理員、經理核可）。
6. LLM 服務放哪裡、哪些欄位允許送出（事件含機台、批號、量測值）。

## 4. 引擎寫死的假設：客戶端無法只靠填資料解決

以下寫死的內容來自原始碼。「欄位不同時的行為」欄標 * 者是 2026-11-01 在示範資料上的實測，其餘由原始碼推得、未實測。

| 寫死的內容 | 在哪裡用 | 欄位不同時的行為 |
|---|---|---|
| 事件情境欄位：`Produce_No.`、`Semi_produce_No.`、`timestamp`、`P1.Machine_No.`、`P1.Material`、`Slitting date`、`Slitting machine`、`Winder number`、`Quality inspection`、`Quality control`、`P3.Machine_No.`、`P2.NG_code`、`P3.NG_code` | 序列化器組事件情境 | * 欄位改名後**成功但情境全為空**（實驗：機台欄位改名，6 筆事件的機台全為 None，沒有任何錯誤） |
| 不良代碼欄位只有 `P2.NG_code`（observer 為 P2）或 `P3.NG_code`（其他，含 All） | 每日模式 B 層訓練 | 欄位改名則所有樣本被跳過，分布庫為空（客訴模式會因空庫而大聲失敗，但每日模式不會） |
| 環境特徵固定七項（P1 機台、材料、分條機、收卷軸、質檢、品管、P3 機台） | B 層的分布與評分權重 | 沒有這些欄位的場域，環境分數恆為 0，B 層只剩異常特徵與關鍵指標兩項 |
| 搜尋關鍵的類別欄位固定八項 | C 層相似案例 | 同上；相似案例要求其中除產品編號外的七項全部相同（產品編號一併比對是 2026-11-01 發現並修正的錯誤） |
| `Slitting machine` | 相似度的機台比對 | 缺欄位時，A 層在描述性階段就報錯（可接受） |
| `observer` 只認 P1／P2／P3／All；`feature` 的站點名稱在 All 下可任意 | 設定載入 | * **填別的值會被悄悄改成 All，只印警告**（實驗：`observer: LINE1` 成功，沿用 All） |
| 清理資料時刪除含任一空值的列 | 待分析資料 | * 空值列**悄悄消失**，結果只顯示筆數變少（實驗：一列有空值，6 筆變 5 筆，沒有說明） |
| 基準資料在客訴模式不做清理 | 基準 CSV | * 基準有空值或文字：PCA 報「Input X contains NaN」，沒說是哪一欄（實驗：2 項皆如此） |
| 拓樸特徵的名稱必須與 CSV 欄名一致 | 製程位置對應 | 對不上的特徵**被略過**，位置對應變少 |
| SOP CSV 以逗號切欄，需要七欄；欄位內有逗號會錯位；標題列也被當成一筆知識 | SOP 檢索與搜尋關鍵 | 少於七欄的檢索結果被略過，只在日誌留一行警告 |
| `score_breakdown` 以 40／30／30 正規化 | 相似度 | 評分權重改變需改程式 |

同一次實驗裡**直接報錯**、因此可接受的：缺目標欄位、缺類別欄位（`Slitting machine`、`P3.NG_code`）、基準缺一個設定的特徵（訊息為「feature names should match」，沒指出是哪一個）、基準含文字。

**結論：** 要讓不同場域能只靠欄位字典導入，需要在 Kit 加一層**欄位對照**（場域欄名 → 引擎欄名），並在啟動前驗證。這是目前最大的缺口。

## 5. 資料品質實測（示範資料上，客訴模式 A+B）

| 情境 | 結果 | 判讀 |
|---|---|---|
| 基準 80／20／14／13／12／8／3 列（12 個數值特徵） | 全部成功，預測相同 | **沒有最少列數保護**；3 列基準算出的 PCA 與界線沒有統計意義，Kit 不警告 |
| 基準含空值 | 失敗，訊息不含欄位 | 大聲失敗，但不好處理 |
| 基準一欄全為同一個值 | 成功 | 無保護（變異為零） |
| 待分析資料一列有空值 | 成功，少一列 | 悄悄略過，應該列出被略過的列 |
| 待分析資料只有一列 | 成功 | 可以，但相關性比較不可靠 |
| 待分析資料兩列 ID 重複 | 成功，事件少一件（6 變 5） | 悄悄合併，應該在啟動前就拒絕 |
| 缺目標、缺類別欄位、基準缺特徵 | 失敗 | 大聲失敗 |
| 欄位改名（機台、不良代碼） | 成功但情境為空 | **悄悄退化** |
| `observer` 填未知值 | 成功，改用 All | **悄悄替換** |

另外：沒有適用所有場域的最低筆數。需依特徵數、變異與正常條件的涵蓋評估；基準列數至少要大於特徵數，才談得上 PCA。

## 6. 建議的導入流程

| 步驟 | 內容 | 負責 | 產出 |
|---|---|---|---|
| 1 | 填需求表：要啟用的層、分析問題、一列的定義、期間與筆數、LLM 服務位置、驗收人 | client＋整合方 | 需求表 |
| 2 | 交五樣最小資料（待分析、基準、欄位字典、品質與不良說明、製程流程說明） | client | 原始檔 |
| 3 | 整理成引擎欄位並產生分析設定檔 | 整合方（可用 AI 協助草稿，client 確認） | 設定檔、整理後 CSV、整理報告（清理前後筆數） |
| 4 | **用 20 至 50 列的小批資料試跑 A 層** | 整合方 | 試跑結果、被略過列與欄位的清單 |
| 5 | 補不良代碼與歷史標註，每日模式訓練分布庫，客訴模式試跑 B | client 提供標籤，整合方執行 | `known_base.json` |
| 6 | 補拓樸與 SOP，啟用 C；先用 `builtin-hash`，確認流程後換 E5；接 LLM 服務 | client 提供內容 | 拓樸、SOP CSV、LLM 位址 |
| 7 | 以真實客訴驗收；對確認的事件提交回饋，發布第一個案例庫版本 | client 經理與管理員 | 案例庫 v0001 |
| 8 | 驗收清單（見下） | client 驗收人 | 簽核 |

驗收重點：能由事件編號回查原始樣本；各階段無未處理的錯誤；LLM 服務失敗時分析標為失敗而不是完成（轉接層已改為失敗回 502）；統計關聯、規則分數與人工確認原因分開呈現；確認的結果下一次分析讀得到（需不同產品編號也找得到，這點在本日實測發現並修正）。

## 7. 建議的 Kit 改進（依價值排序）

狀態（2026-11-01）：#1、#2、#3 已實作，見 `docs/analytical-four-kit.md` 第 10 節與決議 D144；其餘未做。

| # | 改進 | 解決什麼 | 規模 |
|---|---|---|---|
| 1 | **欄位對照**：分析設定加場域欄名到引擎欄名的對照表，啟動前套用；缺欄位在就緒檢查就列出 | 第 4 節三種悄悄退化；讓 client 不必改自己的欄名 | 中 |
| 2 | **就緒檢查加資料驗證**：必要欄位存在、`observer`／`method`／`mode` 值合法（不再悄悄替換）、ID 不重複、基準列數大於特徵數、基準無空值並指出欄位 | 第 5 節的悄悄結果與難懂訊息 | 小 |
| 3 | **執行紀錄揭露清理結果**：被丟棄的列數與原因、被略過的特徵、拓樸對不上的特徵、SOP 解析失敗筆數 | 悄悄略過 | 小 |
| 4 | **範本下載**：Kit 提供空白的欄位字典、需求表、各檔的欄位說明與範例（已有合成示範資料可當範例） | client 不知道交什麼 | 小 |
| 5 | **匯入驗證報告**：上傳資料檔時先出一份檢查報告再決定是否放進資料目錄（目前沒有上傳介面，檔案靠部署端放入） | client 自助 | 中 |
| 6 | 拓樸／SOP／NG 定義的格式檢查器 | 第 4 節拓樸與 SOP 的悄悄略過 | 小 |

建議先做 #1、#2、#3：它們把「悄悄」變成「大聲」，也是 client 可自助的前提。#5 之後再看是否需要上傳介面。

## 8. 還需要 client 回答的問題

- 新場域有沒有「站點」概念？沒有的話，`P1／P2／P3` 的分組與 `observer` 要如何對應？
- 不良標籤是人工確認的真值，還是系統判定？
- 資料是否含需要去識別化的欄位（批號、人員）？送到 LLM 前是否需要遮罩？
- LLM 服務是內部自建還是外部服務？若是外部，資料是否允許出廠？
- 每天的資料量與事件量？決定逾時與是否需要排程。
