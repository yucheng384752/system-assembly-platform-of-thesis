**PDF 轉 CSV 的比法（U11 納入；比法是 Claude 的建議，未經 user 確認）：**

- 事實（讀來源程式碼與 `dev-guides/PDF_TO_V2_IMPORT_SPEC.md`，未執行）：轉檔由外部的 PDF 轉檔服務完成，網址設定在 `PDF_SERVER_URL`（`app/core/config.py`），未設定時端點回錯誤；服務回傳 CSV 壓縮檔；轉出的 CSV 先成為可檢視、可編修的項目，使用者修正後再送驗證與匯入。規格文件說明轉檔服務「會產生多個錯誤內容」，所以才需要人工修正。
  - 更正（2026-11-11，讀程式碼確認，見 `docs/thesis-source-inventory.md` 第 2.3、4 節）：原先寫「去重以 PDF 的 sha256 判斷」是照規格文件，與程式碼不符。`POST /api/upload/pdf` 沒有雜湊檢查；去重發生在建立匯入工作時，比的是 CSV 內容的 SHA-256，使用者確認後可放行。另外，一份 PDF 可能轉出多份 CSV，轉出的 P2 CSV 會被注入收卷機編號後寫回。
- 文件互相矛盾：`dev-guides/VALIDATION_MECHANISMS.md` 說轉檔後自動驗證，`PDF_TO_V2_IMPORT_SPEC.md` 說轉檔後不自動驗證。結論（2026-11-11，讀程式碼）：不自動驗證。背景只建立不驗證、畫面也不讀的上傳工作；畫面取回 CSV 後由使用者手動按驗證。
- 建議：外部轉檔服務不屬於任何一方系統，兩邊都接同一個假服務。對同一份合成 PDF，假服務固定回傳同一個合成 CSV 壓縮檔，也要有回傳錯誤與逾時的情況。這樣 S4 比的是系統如何處理轉檔結果（建立上傳工作、可編修、去重、送驗證），不比轉檔品質。
- 轉檔品質與真實轉檔服務不在判準內，論文寫為限制。
- 產出系統目前的狀況要先查：`kits/upload-validation-kit` 有 `services/pdf_conversion.py`（D90 自基線組裝輸出複製），但它在產出系統能否運作、預覽是否涵蓋，Claude 沒有驗證。

### 4.4 兩個必須寫進論文的限制

1. **Kit 的程式碼出自同一個來源系統。** `kits/form-analysis.kit-manifest.json` 的 `sourceSystem.path` 就是這個來源專案，`kits/BASELINE.md` 也記載 Kit 複製自基線版，而基線版由這套系統拆出。所以「復現」有一部分是把原系統的程式重新組裝。論文必須分開說明：哪些行為由畫布決定，哪些是沿用的 Kit 程式碼。否則「AoV 完成了轉換」的說法站不住。建議在 S3 的統計之外，另列一張「每個節點的行為來自畫布設定還是 Kit 既有程式」的表。
2. **來源專案的資料是未去識別化的真實資料。** user 確認 `test-data/` 尚未去識別化（U8）；其餘的 `.env` 類檔案、`uploads/` 資料夾與根目錄及 `form-analysis-server/` 下的 CSV（檔名帶批號樣式）沒有人確認過，一律比照處理。Claude 沒有打開過這些檔案。規則：
   - 來源專案唯讀，只讀文件與程式碼。
   - 不讀 `.env`、`.env.*`（範例檔除外）。
   - 不把來源的資料檔複製進本專案、測試 fixture、論文或任何外部服務（含 LLM）。
   - S4 的輸入檔一律依程式碼與文件中的欄位格式自己製作合成資料。欄位格式從程式碼（例如 `csv_field_mapper.py`、驗證規則）讀，不從資料檔讀。
